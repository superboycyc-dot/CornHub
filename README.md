# CornHub

CornHub 利用收割前后的卫星观测，估计加州选定样区在 2022 至 2026 年各收获年度有多少英亩玉米用于青贮（Silage，S），多少用于籽粒（Grain，G）。我们希望帮 USDA 统计人员做一个具体决定：**如果只能再核查三块田，先查哪三块，最有机会改善面积估计？**

**2026-11-14 · 方案已确定，效果待验证。** 五个席位待认领。研究范围限定为美国加利福尼亚州，时间为 2022 至 2026 年（含首尾）。拿到官方 sample notebook 后，先筛出符合范围的记录，再根据有效标签确定州内样区和验证规模。

## 数据范围与验收

所有分支使用同一范围：田块及观测位于加州，带日期的观测、标签和统计资料限 2022-01-01 至 2026-12-31，收获年度限 2022–2026。全国数据源先按加州边界裁剪，再提取特征；训练、校准、验证、核查模拟和地图均使用筛选后的数据。静态州界作为裁剪依据。

数据成员按年份列出样区、田块数、有效标签数、已覆盖英亩数和最后观测日期。地图按收获年度分别展示；当年资料尚未齐全时标明截至日期和缺口。州内局部样区的结果只代表其覆盖范围。

### 由资源清单确定的建模顺序

1. **先使用挑战方样本。** 以官方 Notebook 提供的标签、边界和样区为主键，先核实标签是否真的是最终收获用途、单位/年份是否一致、是否存在一田多记录。官方样本尚未加入本仓库；没有标签时不能训练或报告 S/G 分类性能。
2. **玉米筛选与田块单元分开处理。** CDL 可给玉米像元掩膜，但不是田块边界，也不标注收获用途。比赛样本若含田块多边形，以其为田块单元；若没有，先用连通区域/聚合像元形成“候选区域”，明确它不是官方地块边界。运营版若要在收获当年 1 月前估算，使用上一年 CDL 或当季可用的玉米范围输入，并标记候选范围误差。
3. **核心时序优先 Sentinel-2。** 对每个田块按日期提取云/阴影过滤后的红光、近红外反射率，计算 NDVI；同步记录有效观测覆盖率、日期空档和收获前后变化。Landsat 用于延长历史或补充缺测，作为可选项，不阻塞 Sentinel 基线。
4. **天气是解释变量，不是收获标签。** 第一版可选加入 gridMET 的温度/降水窗口，测试是否减少“干旱早衰被误判成青贮”等错误。Daymet 用于历史回测；只有其完整年度数据到齐后才用于对应年份。
5. **用 NASS 汇总做总量核验。** 逐田留出评估检验分类；县/州 NASS 统计用来检查汇总面积是否明显偏离官方量级。两种验证不能混为一谈：总量接近并不证明逐田分类正确。
6. **需求/运输做第二阶段。** 首版输出县域或奶牛场服务区的青贮概率加权面积；需要公开的县级奶牛存栏/牛奶生产统计时，先从 Quick Stats 核对可用字段。场级需求、实际库存、农场 GPS 轨迹、卡车吨位与路线限制不在 Resources 清单内；缺少这些数据时只展示“供给信号与邻近奶业区”，不声称已完成实时供需匹配或配送优化。

### 目标输出与诚实的不确定度

每次运行至少给出：数据截至日期、候选玉米面积、有效观测面积、青贮面积估计、分类置信区间/低置信面积、云遮与缺测比例、模型验证样本数和青贮类 Precision/Recall/F1。可选吨数用地区单产换算并单列单产假设；不能把 21.8 吨/英亩的全国 2025 平均值当作每个州、县或田块的固定产量。类别约 94% 籽粒、6% 青贮的分布会让“全猜籽粒”看起来准确，因此同时报告青贮类指标与该朴素基线，不能只报总准确率。

## 从田块观测到核查决定

1. **确定能统计的面积。** 选定收获年份和样区，确认纳入计算的田块属于目标玉米收获范围，统一使用英亩并去重。记录可分类面积与缺测面积。只有掌握样区玉米收获总面积时才报告覆盖率，否则明确汇总仅代表已覆盖田块。
2. **从变化过程判断用途。** 检验两个线索：植被仍绿时突然下降，是否更常见于青贮；收割前持续变干，是否更常见于籽粒。以真实用途标签检验这些关系。雨养青贮也可能提前变黄，云遮也可能让渐变看似突变。标出观测空档，在有数据时结合降水或灌溉解释反例。最终分类标签是收获用途，收割时间与方式提供辅助证据。
3. **给出概率并检验可信度。** 从 Random Forest 基线开始，按田块分组，防止同一田块的多次观测跨越训练和评估集合。样本允许时用独立数据校准概率，报告保留田块数、F1 和 Brier Score。标签太少时展示逐田结果和误判原因，将统计结论标为探索性。
4. **计算面积并安排复核。** 对每块可分类田，记面积为 A、青贮概率为 p。青贮面积估计为各田 A × p 之和，籽粒面积估计为各田 A × (1 − p) 之和，两者应加总到可分类面积。假设一次核查能确认整块田的用途、各田核查成本相近，第一版用 A² × p × (1 − p) 排序。它衡量单块田给青贮面积带来的估计方差，兼顾田块大小和分类不确定性。清单同时呈现英亩数、概率和观测缺口，方便人工判断。
5. **用同一笔核查预算验证价值。** 在有真实面积和标签的保留田块中先隐藏标签，生成初始面积和清单。分别按清单和随机顺序核查相同数量的田块，例如三块。每揭开一个标签，就用确认的青贮面积（整块面积或零）替换原估计。最后用全部保留标签算出真实总数，比较核查前后青贮面积的绝对误差（英亩）。随机抽取重复多次，报告误差的中位数和范围，如实呈现两种策略的结果。
6. **现场展示。** 先报两类面积及覆盖范围，再打开优先清单里的一块田，解释卫星看见了什么、哪里还有疑问，最后展示确认用途后区域数字如何修正。产值和市场影响可放在附录说明应用背景。


## 怎样维护主线

`main` 保存已经集成的成果，本页记录里程碑。每次把讨论结果发给主控 AI，它将决定整理为“日期、决定、负责人、验收条件”，把待办拆成 GitHub Issues，记录依赖和阻塞。成员 AI 从自己的固定分支同步最新 main，完成一个可验证的改动后向 main 提交 Pull Request，附关联 Issue、产物和验证结果。主控 AI 审查接口、复现结果、处理冲突并合并，更新进度。合并后保留五条分支供下一轮继续使用。

仓库所有者掌握 GitHub 管理权限；主控 AI 在获授权的会话内使用该权限协调工作。需要 DeepSeek 等模型参与时，由所有者指定任务、可共享材料和模型，再把结果纳入同一审查流程。
